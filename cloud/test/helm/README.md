# Helm template tests

Golden-file tests for the GCP charts. Each case renders one chart with the value files and Helm parameters that the corresponding ArgoCD `Application`/`ApplicationSet` would inject in production, and diffs the output against a checked-in expected file.

## Running

From this directory (`cloud/test/helm`):

```sh
./test-render.sh                 # check mode — exits non-zero on drift
./test-render.sh --update        # regenerate expected/ from current charts
```

The runner needs `helm`, `yq` (mikefarah v4), `diff`, `sed`, and `grep` on `PATH`.

## Workflow: I changed a chart, what do I do?

The default flow is **review the diff, then update the goldens**.

1. Run `./test-render.sh`. The first failing case prints a unified diff (truncated to ~80 lines).
2. Read the diff. Decide whether the change is intentional (your edit caused it) or accidental (unrelated regression).
3. If intentional: run `./test-render.sh --update`, then `git diff cloud/test/helm/expected/` to see the full impact across all cases. Sanity-check it. Commit `expected/` alongside your chart change.
4. If accidental: fix the chart, re-run `./test-render.sh` until clean.

`./test-render.sh --update` writes every case's current output to `expected/<case>.yaml`. If your change should affect only one chart, expect changes in only the cases that render that chart. A diff in `liferay-infrastructure-provider.yaml` after editing `helm/gcp-infrastructure/` (instead of `helm/gcp-infrastructure-provider/`) is a red flag.

The PR diff on `expected/` is the most important review surface for the change. Reviewers can see exactly what manifest the chart now produces — it's a much better signal than "I changed `if` on line 42 of a template".

## Workflow: I changed `argocd.tf`'s Helm parameters

`cases.yaml` mirrors the parameter list each ArgoCD manifest in `cloud/terraform/gcp/gitops/resources/argocd.tf` injects. Each case has a comment pointing at its source resource (e.g. `# mirrors kubernetes_manifest.infrastructure_applicationset, env=dev`).

When you change `argocd.tf`:

1. Find the case(s) in `cases.yaml` that mirror the resource you edited (use the comments).
2. Update the `helm_params` block to match — same keys, same values (substitute concrete sample values for the Terraform expressions: `var.deployment_name` → `sample`, `var.region` → `us-central1`, `local.gateway_name` → `sample-{env}-gateway`, etc.).
3. Run `./test-render.sh --update`.
4. Review the diff in `expected/`. The change to the rendered manifest should match what you expect to happen in production when ArgoCD reconciles.
5. Commit `argocd.tf`, `cases.yaml`, and `expected/` together.

Forgetting step 2 means the test will continue passing while production breaks — that's the only failure mode this layer can't catch on its own.

## Workflow: I changed the sample GitOps repo

The value files in `cloud/samples/gitops-repository/` are the test fixtures. Editing them changes test inputs, which changes goldens.

1. Edit the file(s) under `cloud/samples/gitops-repository/`.
2. Run `./test-render.sh --update`.
3. Review the diff. The sample is also customer-facing documentation — make sure your change doesn't undo a deliberate teaching moment in the sample (e.g. don't add `overlay.bucketName` to the sample's `liferay.yaml` — the whole point of the sample is showing developers don't have to set it).
4. Commit the sample edit and `expected/` together.

## Workflow: I added a new chart

1. Add the chart under `cloud/helm/<your-chart>/`.
2. Add a case to `cases.yaml` with `name`, `chart`, `release_name`, `namespace`, `value_files`, and `helm_params`. If the chart is going to be deployed by a new ArgoCD `Application` you also added to `argocd.tf`, the Helm parameters should mirror that.
3. If the chart has subchart dependencies declared as `repository: file://..` in its `Chart.yaml`, the runner picks that up automatically (`helm dependency update` is invoked for those charts before rendering).
4. Run `./test-render.sh --update`.
5. Inspect `expected/<your-case>.yaml` — confirm it's what you expect.
6. Commit chart, case, and golden together.

## Workflow: A subchart version was bumped

`cloud/helm/gcp` depends on `liferay-default` via `file://../default`. The pinned version lives in `cloud/helm/gcp/Chart.yaml` and is locked in `cloud/helm/gcp/Chart.lock` (generated by `helm dependency update`).

1. Bump the dependency version in `cloud/helm/gcp/Chart.yaml`.
2. Run `./test-render.sh --update` — this re-runs `helm dependency update` and regenerates `Chart.lock`, then renders.
3. Review the diff in `expected/sample-{dev,prd}-liferay.yaml`. These are the only cases that render `helm/gcp`.
4. Commit `Chart.yaml`, `Chart.lock`, `expected/`.

## Workflow: My test failure makes no sense

A few sanity checks before assuming the runner is wrong:

- **Stale `charts/` dir**: `rm -rf cloud/helm/gcp/charts && ./test-render.sh`. `helm dependency update` will rebuild it.
- **Stale local helm cache**: `helm repo update` (only matters if you're using HTTP repos, which this project doesn't).
- **Branch in inconsistent state**: `git status cloud/test/helm/expected/` — if anything there is unexpectedly modified, you may have run `--update` on a branch that already has chart changes from another commit.
- **The "redacted" admin password**: `cloud/helm/default/templates/secret.yaml:4` uses `randAlphaNum 32`, which is non-deterministic. The runner redacts it via `sed` before diffing. If a different Secret starts emitting random bytes, the runner won't redact it — you'll see flapping diffs. Add a redaction line to `test-render.sh` (search for `LIFERAY_DEFAULT_PERIOD_ADMIN_PERIOD_PASSWORD` to find the existing one and copy the pattern).

## Layout

```
test/helm/
├── README.md
├── test-render.sh             # runner; supports --update
├── cases.yaml            # declarative test cases
└── expected/             # one golden file per case, committed
    ├── liferay-infrastructure-provider.yaml
    ├── liferay-resources.yaml
    ├── sample-dev-infrastructure.yaml
    ├── sample-dev-liferay.yaml
    ├── sample-prd-infrastructure.yaml
    └── sample-prd-liferay.yaml
```

Each case in `cases.yaml`:

```yaml
-   name: <stable identifier; becomes expected/<name>.yaml>
    chart: helm/<chart-dir>             # path under cloud/
    release_name: <helm release name>
    namespace: <kubernetes namespace>
    value_files:
        -   <path under cloud/, applied in order>
    helm_params:
        <key>: <value>                  # passed as --set-string
```

The runner:
1. Calls `helm dependency update` on every chart whose `Chart.yaml` declares a `file://..` dependency.
2. For each case, runs `helm template <release_name> cloud/<chart> --namespace <namespace> --api-versions ... -f <each value_file> --set-string <each helm_param>`, redacts the random admin password, and either diffs or writes.

## Notes

- **`--set-string`**: every Helm parameter is passed as a string, matching how ArgoCD `Application` `helm.parameters` are applied in production.
- **`--api-versions`**: defaults are listed under `defaults.api_versions` in `cases.yaml`. Charts in scope today don't use `Capabilities.APIVersions.Has`, so this is forward-compatible insurance, not currently load-bearing. Add to the list if a chart starts gating on a specific API version.
- **`Chart.lock`**: committed for `cloud/helm/gcp/`. The `cloud/helm/gcp/charts/` directory is gitignored — `helm dependency update` rebuilds it.
- **What this catches**: chart template regressions, drift between `argocd.tf` Helm parameters and chart values, subchart upgrades that change rendered output, accidental edits to the sample GitOps repo.
- **What this does not catch**: runtime behavior, Crossplane composition execution (the goldens contain composition go-template strings as literal text — what they emit at runtime is out of scope), customer GitOps repos that diverge from the sample layout.
