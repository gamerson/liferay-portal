# Client Extensions On Kubernetes

## Status

Design spike for LCD-53515, implemented and exercised in k3d against a simulated Liferay. See **Implementation** for what is real and what is simulated. The prototype chart this evaluates lives at `cne-cookbook/resources/charts/client-extension`.

## Summary

Deploying a Liferay client extension into a cluster is two jobs: delivering a configuration payload to a Liferay virtual instance, and running a workload. The current prototype does both from a Helm chart. Helm can express the workload, but it cannot express the ordering dependency between the two, because the workload mounts a ConfigMap that Liferay does not create until it has processed the configuration payload.

This document proposes a `ClientExtension` custom resource reconciled by the existing DXP operator. The operator owns the configuration round trip and the workload; the chart keeps Service, Ingress, and ServiceAccount. The custom resource embeds a pod template, so the operator creates and owns the Deployment, Job, or CronJob the way a Deployment owns its ReplicaSet.

## Background

### What A Client Extension Is

A client extension has two parts.

1. A **configuration payload** that tells Liferay the extension exists — custom elements, OAuth2 applications, object actions, notification types, and so on.

1. A **workload** that executes: static assets served by Caddy, a batch import, a microservice, or a cron job.

Some client extensions are configuration only and have no meaningful workload.

### The Relationship To A Virtual Instance

A virtual instance can have many client extensions. A client extension belongs to exactly one virtual instance. That is an ownership edge, and making it a first-class, validated field is one of the main reasons to model this as a custom resource.

Microservice extensions communicate with Liferay over trusted channels established by provisioned OAuth2 applications. Those credentials are generated by Liferay at provisioning time and delivered back to the workload, which is what creates the ordering dependency described below.

## How Client Extension Provisioning Works Today

### The Three ConfigMaps

Three ConfigMaps participate, and the chart authors only one of them.

| ConfigMap | Name | Created By |
|---|---|---|
| `metadataType: dxp` | `${webId}-lxc-dxp-metadata` | Liferay (`CompanyConfigMapUtil`) |
| `metadataType: ext-provision` | `${release}-${vi}-lxc-ext-provision-metadata` | The chart |
| `metadataType: ext-init` | `${serviceId}-${webId}-lxc-ext-init-metadata` | Liferay (`BaseConfigurationFactory:206`) |

### The Provisioning Round Trip

The `portal-k8s-agent` module inside Liferay watches ConfigMaps labeled `lxc.liferay.com/metadataType=ext-provision`, feeds their JSON through the Felix configurator, and creates the client extension types and OAuth2 applications. The OAuth2 provider then writes the resulting credentials **back** into an ext-init ConfigMap that the workload mounts at `/etc/liferay/lxc/ext-init-metadata`.

A detail that the design depends on: the ext-provision ConfigMap's **labels become OSGi configuration properties**. `LabelsPortalK8sConfigurationPropertiesMutator` copies every label into the configuration dictionary at service ranking 2000, overriding what the build baked into the JSON. A prebuilt artifact can therefore be retargeted at any virtual instance purely by changing a label, with no rebuild.

### Where The Helm Prototype Falls Short

Helm renders the ext-provision ConfigMap and the Deployment in a single pass, but the Deployment mounts a ConfigMap that cannot exist until Liferay has completed the round trip. The pod sits in `ContainerCreating` until it does. The prototype works around this with `mountInitConfig: false` and an empty `podSchedulingGates` entry in `values.yaml` — manual escape hatches for a gap Helm cannot close.

Helm also has no way to report whether the virtual instance accepted the payload, no way to validate that the referenced virtual instance exists, and no defined cleanup story.

## Design

### Ownership Split

| Object | Owner |
|---|---|
| Deployment, Job, or CronJob | Operator, owned by the custom resource |
| ext-provision ConfigMap | Operator |
| Ingress | Chart |
| Mirrored ConfigMaps and Secrets | Operator, owned by the custom resource |
| Service | Chart |
| ServiceAccount | Chart |
| `ClientExtension` custom resource | Chart, rendered from values |

The operator does not template Services or Ingresses. Growing it in that direction turns it into a Helm chart reimplemented in Go.

### Why The Operator Owns The Workload

An earlier revision of this design had the chart template the workload and the custom resource reference it by name, matching the existing `LiferayEnvironment` pattern. That pattern has a defect worth avoiding: two controllers write the same field of the same object. `cloud/helm/default/templates/_statefulset.tpl:28` sets `replicas:` unconditionally, and `liferayenvironment_controller.go:535` writes `statefulSet.Spec.Replicas` with a field owner. Under Argo CD that is a standing out-of-sync and self-heal fight. It is tolerable today only because the licensing ceiling rarely binds.

For client extensions, gating the workload until the ext-init ConfigMap exists is the entire point, so the operator would be mutating a chart-owned object on every reconcile. Embedding the pod template instead makes the operator the sole owner of its child, and Argo CD only ever sees the custom resource.

Embedding also removes an existing wart. Three of the forty-four sample extensions ship `FROM liferay/noop` as `kind: Job` — a container that exists only because the build pipeline must emit a workload. The Dockerfile carries a `# TODO: LPS-176095` comment. When the operator decides, the configuration-only case is an absent `spec.workload` and no child object at all.

### The ClientExtension Custom Resource

```yaml
apiVersion: cx.liferay.com/v1alpha1
kind: ClientExtension
metadata:
    name: liferay-sample-etc-spring-boot
    namespace: team-a
spec:
    liferayEnvironmentRef:
        name: liferay-default
        namespace: liferay-prod
    virtualInstanceId: liferay.com
    serviceId: liferay-sample-etc-spring-boot
    configs:
        - |
          { "com.liferay.object.internal.configuration...": { } }
    workload:
        kind: Deployment
        replicas: 1
        template:
            spec:
                containers: []
status:
    conditions: []
    extInitConfigMapName: liferay-sample-etc-spring-boot-liferay.com-lxc-ext-init-metadata
```

Notes on the fields.

- **`liferayEnvironmentRef`** points at the existing `LiferayEnvironment` resource rather than a bare namespace. That lets the operator refuse to provision against a Liferay that is not activated, and it keeps the one-extension-one-Liferay invariant checkable in one place. An empty `namespace` means the custom resource's own namespace.

- **`serviceId`** must be explicit. It becomes the `ext.lxc.liferay.com/serviceId` label, which is what determines the ext-init ConfigMap name. Inferring it from the resource name reintroduces the naming mismatch described under **Defects Found In The Prototype Chart**.

- **`workload`** is optional. Omitting it entirely means a configuration-only extension with no child objects. `kind` accepts `CronJob`, `Deployment`, or `Job`, and is immutable — validate with a CEL rule rather than silently recreating.

- **`workload.template`** is a verbatim `corev1.PodTemplateSpec`. Kind-specific fields (`backoffLimit`, `replicas`, `schedule`) sit beside it rather than inside it.

The precedent is well established: CronJob embeds a job template which embeds a pod template, KEDA's `ScaledJob.spec.jobTargetRef` is a full job spec, and Argo Rollouts' `spec.template` is a pod template.

### Domains

A client extension is reached at two different addresses, and which one applies depends on who is doing the reaching.

- A **frontend** asset is fetched by a browser, so its `baseURL` must be a publicly routable host.
- A **microservice** is called by Liferay itself, so its `.serviceAddress` should be the cluster-internal Service address when both run in the same cluster.

Liferay resolves both from one input. `BaseURLPortalK8sConfigurationPropertiesMutator` reads the `ext.lxc.liferay.com/mainDomain` annotation, falling back to the virtual instance's own virtual host, and writes it into `.serviceAddress` with `baseURL` derived from it. That annotation is per ConfigMap, not per configuration entry.

So the operator splits the payload. Entries are bucketed by the classification registered for their type, and each bucket travels in its own ext-provision ConfigMap carrying its own `mainDomain`:

| Bucket | Classifications | Annotation |
|---|---|---|
| `internal` | `configuration`, `microservice` | The cluster-local address |
| `public` | `frontend` | The routable host |

```yaml
spec:
    domains:
        internal: auto
        public: cx.example.com
    serviceRef:
        name: my-extension
        port: 8080
```

`internal: auto` expands to `<serviceRef.name>.<namespace>.svc.cluster.local:<serviceRef.port>`, which the operator can compute and a chart cannot. Setting an explicit `host:port` is also allowed. Leaving `internal` empty puts every entry in the public bucket, which is the behavior of the existing chart, so the split is opt-in.

Two limits are worth stating plainly. `.serviceScheme` is taken from the portal's own `WEB_SERVER_PROTOCOL` and cannot be set per bucket, so an internal address is reached over whatever scheme Liferay is configured for. And a client extension whose entries are all frontend, or all microservice, produces a single ConfigMap rather than two — visible as the **Payloads** column in the status report.

### Reconcile Loop

1. Resolve `liferayEnvironmentRef`. Set `Degraded` if it is missing, not activated, or the calling namespace is not permitted.

1. Verify `${virtualInstanceId}-lxc-dxp-metadata` exists in the Liferay namespace. Set `Degraded: UnknownVirtualInstance` otherwise.

1. Create or update the ext-provision ConfigMap in the Liferay namespace, **in place, never delete and recreate**. See **Never Delete And Recreate The ext-provision ConfigMap**.

1. Watch for a ConfigMap labeled `metadataType=ext-init` whose `ext.lxc.liferay.com/serviceId` and `dxp.lxc.liferay.com/virtualInstanceId` labels match. Do not compute its name. Record what is found in status.

1. Mirror the dxp-metadata and ext-init data into the extension's namespace when the namespaces differ.

1. Render and apply the child workload, injecting the volumes, mounts, environment, and labels described below. Do not create it before the ext-init data is available.

### What The Operator Injects Into The Pod Template

- Both volumes and volume mounts: `lxc-dxp-metadata` from the dxp-metadata source, and `lxc-ext-init-metadata` from the **discovered** ext-init source.

- The `LIFERAY_ROUTES_CLIENT_EXTENSION` and `LIFERAY_ROUTES_DXP` environment variables.

- The `dxp.lxc.liferay.com/virtualInstanceId` and `ext.lxc.liferay.com/serviceId` labels.

The injected volume names, mount paths, environment variable names, and label keys are reserved. A user-supplied collision is rejected at admission. The operator is otherwise **additive only** on `spec.workload.template.metadata.labels`: it may add labels but never removes or rewrites what the chart placed there, so the chart keeps control of the labels its Service selects on.

Because the operator does not create the workload until the ext-init data exists, the `mountInitConfig` flag and the scheduling gate workaround both disappear.

### Naming

The child workload's name is exactly the custom resource's `metadata.name`, with no suffix or derivation. The chart names the custom resource with its `fullname` helper, so the Service selector and any future `scaleTargetRef` resolve without guessing.

## The Configuration Payload

### What The Build Produces Today

Developers write `client-extension.yaml`. The `createClientExtensionConfig` Gradle task translates it into `*.client-extension-config.json`, the Felix configurator payload that goes into the ext-provision ConfigMap. The translation lives in `CreateClientExtensionConfigTask` and `ClientExtension.toJSONMap`, driven by a type registry in `client-extension.properties`.

### Translation Rules

Measured across all forty-four sample extensions in `liferay-sample-workspace`, which produce sixty-three YAML entries and sixty-one generated configuration entries.

Every emitted entry carries the same thirteen top-level keys, of which only a handful come from the YAML.

| Generated Key | Source |
|---|---|
| `:configurator:policy` | Constant `force` |
| `baseURL` | `${portalURL}/o/` plus `webContextPath` without its leading slash |
| `buildTimestamp` | `System.currentTimeMillis()` at build, shared by every entry in a project |
| `description` | YAML `description`, default empty |
| `dxp.lxc.liferay.com.virtualInstanceId` | Gradle `liferay.virtual.instance.id`, default `default` |
| `name` | YAML `name` |
| `projectId` | `projectName` lowercased with non-alphanumerics stripped |
| `projectName` | The project directory name |
| `properties` | YAML `properties` map, encoded to a `key=value` list |
| `sourceCodeURL` | YAML `sourceCodeURL`, default empty |
| `type` | YAML `type` |
| `typeSettings` | Every other YAML key, encoded to a `key=value` list |
| `webContextPath` | `/` plus `projectName` |

The configuration key is `${pid}~${yaml entry id}`, where the pid comes from the type registry and the id is the YAML entry's own top-level key. A project with three entries produces three configurations sharing one `projectName`, `webContextPath`, and `baseURL`.

Unrecognized keys always land in `typeSettings` as an encoded list, with list values joined by newlines. They are **additionally** copied to the top level, with native JSON types preserved, whenever the pid is not a `CETConfiguration`. That branch is why `.serviceAddress`, `scopes`, `resourcePath`, and `allowedDomains` each appear twice in the output — once lossily stringified and once with real types.

Five transforms are not pass-through.

1. **Glob expansion.** Any key whose lowercased name contains `url`, with a value containing `*` or `?`, is resolved against the built `static/` directory. `urls: [index.*.js]` becomes `urls=index.58829bb7a75441944031f8527403cf45456d7360.js`.

1. **`frontendTokenDefinitionJSON`** is a file path in the YAML and an inlined minified JSON string in the output.

1. **`scriptElementAttributes`** on `globalJS` is renamed: the map becomes `scriptElementAttributesJSON` with a JSON string value.

1. **`instanceSettings`** consumes its own `pid` key, which becomes the configuration pid with `.scoped` appended and is removed from `typeSettings`.

1. **`homePageURL`** is synthesized for the two OAuth types when absent, as `$[conf:.serviceScheme]://$[conf:.serviceAddress]`.

Entries whose type has no pid in the registry — `batch` and `siteInitializer` — produce no JSON at all. They become plugin package properties and zip layout instead. Their `oAuthApplicationHeadlessServer` cross-reference is silently dropped; the link survives only because the sibling OAuth entry lands in the same configuration file.

### Pure Versus Build Dependent

The translation splits, but not where it would be convenient.

**Pure, and portable to Go.** The envelope, the CET branch, the `key=value` encoding, the type registry, the `instanceSettings` pid rewrite, `homePageURL`, and `scriptElementAttributes`. That is roughly a hundred lines plus a forty-five line properties file.

**Build dependent, and impossible in the operator.** Glob expansion needs to list the built `static/` directory, and `frontendTokenDefinitionJSON` needs to read a source file. Those assets live inside the container image, where the operator cannot see them. **Twenty-two of the forty-four sample projects use a glob**, including every `customElement`, `globalCSS`, `globalJS`, `themeSpritemap`, `fds*`, and `jsImportMapsEntry` sample.

### Recommendation

Port `toJSONMap` to Go and have the operator translate, but carry an **already-expanded** `client-extension.yaml` in the custom resource. The build keeps glob expansion and file inlining, which is where the built artifacts are; the operator does the pure translation, which is where the virtual instance binding is.

The payoff is retargeting: `virtualInstanceId`, `webContextPath`, `baseURL`, and the pid suffixes are all computed in the pure half, so the same artifact can be pointed at a different virtual instance without a rebuild.

Two constraints on the port.

- **`buildTimestamp` becomes the client extension type's `modifiedDate`** in `CETFactoryImpl:75`. Recomputing it on every reconcile churns every modified date and triggers a configuration rewrite loop. Derive it from something stable, such as the resource's `metadata.generation` or a hash of the translated payload.

- **`projectName` is the source directory name** and feeds `webContextPath`, `baseURL`, and the `serviceId` label. It must be an explicit field, not inferred from the custom resource's name.

## Cross Namespace Deployment

Some customers want Liferay in one namespace and client extensions in another.

### The Constraint

The `portal-k8s-agent` is bound to exactly one namespace on both read and write. The informer is `.inNamespace(portalK8sAgentConfiguration.namespace())` at `AgentPortalK8sConfigMapModifier:797`, a single string rather than a list, and the writeback path at line 373 uses the same value. The agent cannot be pointed at the extension namespace, and it certainly cannot watch several. Everything Liferay reads must be in Liferay's namespace, and everything Liferay writes lands there.

### The Three Flows

| ConfigMap | Where Liferay Needs It | Operator's Job |
|---|---|---|
| dxp-metadata | Written to the Liferay namespace, mounted by the extension pod | Mirror into the extension namespace |
| ext-init | Written to the Liferay namespace, mounted by the extension pod | Mirror into the extension namespace |
| ext-provision | Liferay namespace | Create it there directly; it is the author, so no local copy is made |

Volume mounts are namespace-local, which is what forces the two mirrors.

### Owner References

Owner references must be same-namespace. A cross-namespace reference is not rejected — the garbage collector treats the owner as missing and **deletes the dependent**.

- The ext-provision ConfigMap in the Liferay namespace therefore gets **no owner reference**. Clean it up with a finalizer, plus `cx.liferay.com/owner-name` and `cx.liferay.com/owner-namespace` back-pointer labels so orphans can be swept if a finalizer is ever force-removed.

- Mirrors live in the extension's own namespace alongside the custom resource, so they take normal owner references.

### The Shared DXP Metadata Mirror

Several extensions in one namespace bound to the same virtual instance share a single `${virtualInstanceId}-lxc-dxp-metadata` mirror. Keep the mirrored name identical to the source so the pod specification is byte-identical whether or not the namespaces differ, and the chart never learns about the split.

Two guards follow.

- **Same namespace means no mirror.** When the Liferay and extension namespaces match, the mirror *is* Liferay's own object. Writing to it would fight the agent's own modify loop.

- **Conflicting sources are refused, not alternated.** Two extensions in one namespace pointing at the same virtual instance ID in different Liferay namespaces resolve to the same mirror name with different content. Stamp the mirror with `cx.liferay.com/source: ${namespace}/${name}`; if an existing mirror disagrees, set `Degraded: MirrorSourceConflict` on the newcomer and leave the incumbent alone.

Sharing is expressed through owner references. Each extension appends itself with `controller: false` and `blockOwnerDeletion: false`; at most one reference may be the controller, so none of them is. Garbage collection then handles the lifecycle: deleting one extension prunes its reference, and the mirror is collected when the last one goes. No finalizer is needed for the mirror itself.

Do not let every extension reconciler write the shared mirror. That gives N writers racing on one object and couples each extension's reconcile to its siblings. Instead, treat the mirror as derived from a tuple and give it its own reconciler keyed on it.

```
key = (liferayNamespace, virtualInstanceId, clientExtensionNamespace)
```

That reconciler lists the extensions matching the tuple and either deletes the mirror when there are none, or applies the source data and reconciles the owner reference set to exactly those extensions. The `ClientExtension` reconciler never writes the mirror; it only enqueues the tuple. Two watches feed it: the source ConfigMap in the Liferay namespace, fanned out by a map function to every consuming namespace, and the extensions themselves. One writer, one field manager, no contention.

The ext-init mirrors need none of this. They are per-`serviceId` with exactly one consumer each, so a plain controller owner reference is correct.

### Consent

Namespace separation is almost always a tenancy boundary. If anyone who can create a `ClientExtension` in a tenant namespace can make the operator write an ext-provision ConfigMap into the Liferay namespace, they can provision an OAuth2 application with `Liferay.Headless.Admin.User.everything` against someone else's Liferay. The operator holds the cross-namespace write permission and the tenant does not, which makes it a confused deputy.

Consent must come from the target side, in the shape of Gateway API's `ReferenceGrant`. Add an allow list to `LiferayEnvironment`.

```yaml
spec:
    clientExtensionNamespaces:
        - team-a
        - team-b
```

The operator resolves `liferayEnvironmentRef`, checks the extension's namespace against that list, and on failure sets `Degraded: NamespaceNotPermitted` and writes nothing. Same-namespace deployments skip the check.

### Cache Scoping

Cluster-wide ConfigMap access is acceptable for this operator, but the default controller-runtime cache would then hold every ConfigMap in the cluster. Scope the informer by label.

Mirrors need their own `cx.liferay.com/mirror: "true"` label for two reasons: the cache selector has to see them in order to detect drift or manual deletion, and the `lxc.liferay.com/metadataType` label should be stripped from mirrored copies. `AgentPortalK8sConfigMapModifier.clean()` deletes ConfigMaps labeled `metadataType=dxp` whose virtual instance ID does not match a known company. It is namespace-scoped today and cannot reach a mirror, but leaving a live-looking label on a copy is free rope.

## Constraints And Risks

### The ext-init ConfigMap Contains Plaintext Client Secrets

`OAuth2ProviderApplicationHeadlessServerConfigurationFactory:91` puts `${erc}.oauth2.headless.server.client.secret`, the plaintext value from `getPlaintextClientSecret`, directly into the ext-init ConfigMap. That is existing Liferay behavior, but mirroring it across a tenancy boundary copies credentials into a namespace that, by assumption, has different people in it.

**Mirror ext-init into a `Secret` rather than a `ConfigMap`.** The runtime reads `/etc/liferay/lxc/ext-init-metadata` as a directory of files, and a Secret volume produces an identical layout. The operator owns the volume definition, so the chart is unaffected.

### There Is No Error Channel From Liferay Back To Kubernetes

The agent applies configurations and logs failures — a bad scope, malformed JSON, a missing company — without writing anything back. An extension that Liferay rejects sits at `Provisioned: False` with no reason, diagnosable only by reading `liferay.${date}.log`. For a design whose selling point is `kubectl get cx`, this is the weak spot.

The spike can accept it: wait a bounded interval, then report `Degraded` with a generic message. A production version wants a Liferay-side change, either annotating the ext-provision ConfigMap with a per-pid result or introducing an `ext-status` metadata type. Worth filing now so it can be scheduled against a release.

### Never Delete And Recreate The ext-provision ConfigMap

Deletion cleanup works. `_delete` at `AgentPortalK8sConfigMapModifier:231` lists configurations matching `(.k8s.config.uid=${configmap uid})` and deletes them, and `BaseConfigurationFactory:104` strips the ext-init entries on deactivate. A finalizer that deletes the ConfigMap genuinely unprovisions the types and OAuth2 applications.

The match key is the ConfigMap's **UID**. Recreating rather than updating makes Liferay observe a delete followed by an add: the OAuth2 application is torn down and rebuilt with a **new client secret**, while every running pod still holds the old one until the mirror propagates. In-place update must be a hard rule in the reconciler, never `Delete` plus `Create` as a resync shortcut.

Two consequences for the finalizer.

- Unprovisioning requires Liferay to be running. If it is down when the extension is deleted, OAuth2 applications leak in the database. Wait for the ext-init data to disappear as the acknowledgement, bound the wait so namespace deletion cannot hang, and log loudly on force-release.

- `_modifyConfigMap` short-circuits unless `_clusterMasterExecutor.isMaster()`, so on a clustered Liferay the writeback happens only on the master and stalls during failover. Size the `Provisioned` timeout in minutes.

### Microservice Callback Addressing

`BaseURLPortalK8sConfigurationPropertiesMutator` sets `.serviceAddress` from the `ext.lxc.liferay.com/mainDomain` annotation, falling back to the company's virtual hostname, and does so unconditionally -- the `localhost:58081` in the sample YAML files is always replaced.

The bucketed ext-provision ConfigMaps described under **Domains** work around this without any change to Liferay, because the annotation is per ConfigMap. What remains unavailable is a per-bucket `.serviceScheme`: that value comes from the portal's own `WEB_SERVER_PROTOCOL`. A cluster-internal service that only speaks HTTP while Liferay is configured for HTTPS therefore cannot be expressed, and is the one addressing case still needing a Liferay-side change.

### Smaller Notes

- **CRD versioning.** Ship `v1alpha1` and expect to break it. An embedded pod template makes a conversion webhook genuinely unpleasant, so settle the shape while it is still allowed to change.

- **Latency is normal.** `debounceDelayMillis` defaults to 300ms and `modifyConfigMap` returns `BUFFERED`, with informer resync and mirror reconcile on top. Several seconds between apply and `Provisioned: True` is healthy.

- **One Liferay per namespace.** The agent selects ext-provision ConfigMaps by label alone, with no notion of which Liferay owns them. Two installations sharing a namespace would both consume every extension. The design avoids this by construction, but the invariant should be stated.

- **Virtual instance deletion.** `VirtualInstanceCustodian.clean()` deletes dxp-metadata ConfigMaps for companies that no longer exist, pulling the mirror source out from under live extensions. Surface it as `Degraded: VirtualInstanceGone` rather than serving a stale mirror.

- **Volume propagation.** Kubelet refreshes mounted ConfigMap and Secret volumes in place, so a virtual host change reaches running pods without a restart, with roughly a minute of sync lag on top of the mirror reconcile. This holds only for whole-directory mounts; `subPath` mounts never update.

### Running It

```bash
cloud/operator/hack/run-all.sh
```

That creates a k3d cluster, builds the operator and the simulator, installs the CRDs and the operator chart, builds an image for every sample in `liferay-sample-workspace`, runs all three scenarios, and writes the status report. `teardown.sh` removes the cluster.

### What Is Simulated

`dxpsim` reproduces the observable contract of `portal-k8s-agent`: it watches ext-provision ConfigMaps in one namespace, treats their labels as configuration properties, resolves addressing from the `mainDomain` annotation, provisions an OAuth2 application per `oAuthApplication*` entry, writes the credentials back into `<serviceId>-<webId>-lxc-ext-init-metadata`, and withdraws them when the source ConfigMap disappears.

It serves no HTTP and has no database. It exists so the handshake can be exercised without a licensed DXP boot, and it is not a substitute for testing against real Liferay.

### Results

- The Go translator reproduces the Gradle task's payload for **44 of 44** sample projects, compared entry by entry against the checked-in `*.client-extension-config.json`. Encoded `typeSettings` are compared as sets: the Go implementation sorts them, where the Gradle task's `HashMap` iteration order is unstable and would churn the ConfigMap on every reconcile.
- All **44 of 44** client extensions reach `Delivered` and `Provisioned` in both the same-namespace and split-namespace scenarios.
- A client extension in a namespace absent from `clientExtensionNamespaces` is refused with `Degraded: NamespaceNotPermitted`, and nothing is written into the Liferay namespace.
- Seven workloads do not reach `Ready`. All seven are runtime failures caused by the simulator rather than by the operator, and are itemized in the status report.

### Deviations From This Document

The shared virtual instance mirror is reconciled inside the `ClientExtension` reconciler rather than by a second reconciler keyed on `(liferayNamespace, virtualInstanceId, clientExtensionNamespace)`. The write is idempotent and the owner reference append converges, so concurrent reconciles agree, but a dedicated single-writer reconciler is still the better shape and remains the intent.

## Out Of Scope For The Spike

- **HorizontalPodAutoscaler.** Deferred. With it out, the operator unconditionally owns `spec.replicas`. If autoscaling returns, the operator must omit `replicas` entirely when `spec.workload.replicas` is nil, leaving the field for the autoscaler, or the two will fight over it exactly as described under **Why The Operator Owns The Workload**.

- **The CoreDNS hooks.** `templates/hooks/` patches CoreDNS from a Job in `kube-system` with its own RBAC. It is a local development convenience and should not be carried into a production chart or the operator.

- **Service and Ingress ownership.** These stay in the chart.

## Defects Found In The Prototype Chart

These are worth fixing regardless of whether the operator is built.

1. **`_helpers.tpl:12` never resolves to the release name.** Sprig's `default` returns the first non-empty of its *given* arguments, so `default .Release.Name .Values.nameOverride .Chart.Name` always yields `liferay-client-extension` unless `nameOverride` is set. That value becomes the `ext.lxc.liferay.com/serviceId` label, so Liferay names the ext-init ConfigMap `liferay-client-extension-${webId}-lxc-ext-init-metadata` while the chart mounts `${releaseName}-${vi}-lxc-ext-init-metadata`. They match only by accident, and the pod hangs in `ContainerCreating` when they do not. Watching for the ConfigMap by label instead of reconstructing its name eliminates the whole class.

1. **`virtualInstanceId` must be the company web ID**, such as `liferay.com`, not `default`. The chart uses it to name `${vi}-lxc-dxp-metadata`, and Liferay derives that name from `company.getWebId()`. The `default` value in the generated sample configurations is misleading, and is overridden by the ConfigMap label in any case.

1. **`hooks/post-install.yaml:38` and `hooks/pre-delete.yaml:38` reference `.Values.clientExtensionConfig.domain`**, a value that does not exist. The field is `mainDomain`, so both CoreDNS hooks pass an empty argument.
